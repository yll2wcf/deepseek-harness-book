# 第1章 Agent 不是一个聊天接口

第一次打开 DeepSeek Harness，我最容易犯的错误，是把注意力全部放在模型上：它用了哪个模型，提示词写在哪里，又有哪些工具。

真正把项目跑起来以后，我才发现，模型只占运行过程的一段。模型前面有配置、工作区、系统提示词和权限，模型后面有工具、事件日志、恢复和界面。少掉其中任何一部分，我们得到的都更像一次 API 调用，而不是一个能够继续工作的 Agent。

这一章先不分析 Agent Loop，也不追某个工具怎样执行。我们的目标更朴素：在隔离环境中把项目跑起来，分清源码目录、Harness Home 和工作区，观察 Web 与 Headless 两种入口，并建立第一份运行记录。

完成以后，你应该能回答一个基础问题：当我向 Agent 发送“总结这个仓库”时，除了模型回答，系统还必须决定什么？

如果你已经克隆过项目，也请先核对版本和运行目录。源码书最怕两个人读着不同提交，却把输出差异误判成自己操作错误。

## 一段回答和一个运行系统差在哪里

最小的大模型调用很容易理解：准备消息，调用接口，接收文本。

~~~ts
const answer = await model.generate({
  messages: [{ role: 'user', content: '总结这个仓库' }],
})

console.log(answer.text)
~~~

这段代码可以回答问题，却没有说明模型能读取哪个仓库、是否可以运行命令、工具失败以后怎样继续、用户取消时清理什么，也没有保存能够恢复的执行事实。

Harness 解决的是这段调用周围的工程问题。它至少要知道：

- 从哪里接收任务，怎样区分一项新工作和当前工作的补充信息。
- 当前 Agent 能访问哪个工作区，拥有哪些工具和模型。
- 哪些动作可以直接执行，哪些动作需要询问或拒绝。
- 模型调用、工具调用和最终结果怎样进入会话记录。
- 当前运行怎样结束，失败、取消和进程退出以后留下什么。
- 同一套核心怎样被 Web、一次性命令、SDK 或自动化协议使用。

因此，DeepSeek Harness 这个名称里的 Harness，不只是“帮模型接上几个函数”。它是承载模型、工具、状态、策略和运行入口的一套系统。

> 核心建议
> 第一次观察 Agent，不要只保存最后一句回答。把启动方式、工作区、模型、工具、审批、事件和终态一起记下来。最后一句话可能变化，这些运行事实才是阅读源码的坐标。

## 先接受它仍处在开发者预览阶段

本次修订固定到2026年11月13日拉取的上游 `master` 提交 `e8f7b93a344964de3dca1ace9e72b6e4d6de87cb`，根 `package.json` 的版本号是 `0.2.2-rc.2`。该提交不等同于同名发布标签，阅读时以提交为准。[根目录 README](https://github.com/deepseek-ai/deepseek-harness/blob/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb/README.zh.md)仍将项目标为开发者预览，[安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb/SAFETY.zh.md)说明它没有完成安全审计，不应被当成可直接用于生产环境的软件。

这不是一句可以跳过的提醒。DeepSeek Harness 能执行模型生成的代码和命令，能加载第三方插件，也能访问你向它开放的文件、进程、网络和凭据。模型输出错误、配置错误或不可信插件都可能产生真实损害。

沙箱、权限模式和审批提示能够降低风险，但不能保证绝对隔离。尤其是已经授权给 Harness 的资源，沙箱不会替你判断其中哪一份文件最重要。

第一次运行时，我建议做四件事：

1. 使用专门的学习目录，不要把主目录或重要工作仓库直接开放给 Agent。
2. 使用隔离的 `DSH_HOME`，不要让实验配置和会话混进日常环境。
3. 不放入生产凭据、客户数据和无法恢复的文件。
4. 先运行只读任务；看清工具调用和审批行为以后，再尝试写入操作。

如果条件允许，一次性虚拟机、容器或专用测试设备比个人主机更合适。无论运行在哪里，都应先备份 Harness 能够访问的数据。

## 先固定版本，再安装和构建

本书后续命令都假定你位于 DeepSeek Harness 仓库根目录，并使用同一份源码基线。第一次准备环境时依次执行：

~~~sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
git switch --detach e8f7b93a344964de3dca1ace9e72b6e4d6de87cb
node --version
pnpm --version
pnpm install
pnpm run build
~~~

`git switch --detach` 把工作区固定到本书使用的提交，不会创建用于开发的本地分支。执行 `git rev-parse HEAD`，应得到上面的完整提交号。准备自行修改上游代码时，再从这个位置创建自己的开发分支。

当前基线要求 Node.js `>=24.9.0`，仓库声明 pnpm `11.28.5`。旧稿使用的 Node.js `v22.22.0` 已不满足要求，不能沿用旧环境解释新版启动结果。先按仓库开发指南切换运行时，再安装依赖。

本次修订实际确认了默认 Node.js 仍为 `v22.22.0`，另有可用的 Node.js `v24.22.1`。尝试用后者运行 `pnpm dsh --help` 时，pnpm先要求重新安装工作区依赖，随后以 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` 结束。因此，本章安装、构建、配置导出和启动命令已按当前源码核对，但未在新版完成运行验收。请把自己的成功输出另记为本机证据。

根脚本中的 `pnpm dsh` 使用 `node --import tsx/esm` 执行 [`apps/cli/src/bin.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb/apps/cli/src/bin.ts)。CLI 入口直接来自 TypeScript 源码，但 Host、Client 和 Web 前端仍需要构建产物。`pnpm run build` 现在并行执行产物构建与构建检查；日常开发可先执行 `pnpm run build:artifacts`，最后执行 `pnpm run build:check`。全新 checkout 或更新源码后，不应把旧产物当成新版验收结果。

根 README 也提供已发布版本的 `npx` 用法，但本书后续统一从源码运行。只有这样，屏幕上的现象、文中的文件路径和你正在阅读的实现才属于同一个版本。

## 三个目录看起来相近，责任完全不同

运行 `dsh` 以前，先分清三个位置。后面很多“找不到文件”和“配置为什么没有生效”，都源于把它们混成一个目录。

| 位置 | 保存或决定什么 | 最常见的误解 |
|---|---|---|
| 源码目录与启动目录 | 仓库源码、依赖和构建产物；`process.cwd()` 从这里开始 | 误以为它就是用户配置目录 |
| Harness Home | Profile、用户设置、凭据引用、会话和其他运行数据 | 误以为换工作区会自动换 Home |
| 会话工作区 | Agent 本次可以读取、修改和运行命令的项目位置 | 误以为 Web 启动后自动选中了当前目录 |

随书实验统一在命令前加上 `env DSH_HOME="$PWD/tmp/deepseek-harness-book/runtime-home"`，把 Harness Home 放到书稿目录下。这样，Profile 和运行数据不会写入个人默认 Home。这个目录仍然可能包含设置、会话或凭据引用，不应提交到公开书稿仓库。

进程启动目录会成为默认文件系统位置，但全新的 Web UI 不会自动选中任何工作区。打开页面后，需要点击“选择工作区”，添加并选中项目目录，输入框才可使用。也就是说，终端里的 `pwd` 是一个后备位置，不等于某个会话已经获得了这个工作区。

以后遇到 Agent 报告“文件不存在”，先记录三项：终端 `pwd`、当前 `DSH_HOME`、界面里选中的会话工作区。不要一上来修改提示词。

## 配置导出是第一次运行的体检单

直接启动 Web 会把配置解析、插件挂载、端口监听和浏览器访问放在一起。任何一层失败，终端都可能只留下一个很长的错误栈。第一次接触项目时，先用 `--dump-config` 查看最终插件树更稳妥。

~~~sh
env DSH_HOME="$PWD/tmp/deepseek-harness-book/runtime-home" \
  pnpm dsh --profile web --dump-config
~~~

这条命令组合 Bundle、Profile、Home 和命令行 Overlay，却不真正启动应用。输出很长，不要从第一行抄到最后一行，只检查五类信号：

1. 基础 Bundle 和 Web Bundle 是否都参与组合。
2. 模型、Session、`ToolsService`、工具执行器和 Agent Loop 等核心行是否存在。
3. Session 使用哪个持久化 Provider，数据目录指向哪里。
4. 默认权限、审批与沙箱相关行是否存在。
5. Web 的 host、port 与启动插件来自哪一层。

当前源码中，Web Profile仍组合 `dsh-base` 与 `dsh-web-app`。基础Patch声明JSONL Session持久化，并通过 `DSH_PERMISSION_MODE` 选择部署覆盖，未覆盖时采用 `workspace-write` 与 `ask`；Web层给出的默认端口仍是3080。这里登记的是源码配置，不是本次成功导出的插件树。不要沿用旧稿的配置行数或模型默认值作为新版输出。

这些结果只证明“最终配置准备这样组装”，不能证明对应插件已经成功激活，更不能证明真实模型已经回答。配置导出、应用启动和业务任务必须分别验证。

`--dump-default-config` 只显示 Bundle 层；`--dump-config` 还会应用 Profile 和 Home 用户层以及指定的 Overlay。以后某个端口或模型配置与文档不一致，可以先比较两份导出，判断差异来自随附默认值还是本机覆盖。

> 核心建议
> 配置导出用来回答“准备装什么”，运行日志回答“是否装成功”，Session 回答“任务实际发生了什么”。三类证据不要互相替代。

## 页面打开了，不等于模型已经可以工作

Web 入口默认监听 `127.0.0.1:3080`。本机启动时通常会打开浏览器，也可以只启动服务器：

~~~sh
env DSH_HOME="$PWD/tmp/deepseek-harness-book/runtime-home" \
  pnpm dsh web --no-open
~~~

`--no-open` 属于 Web 应用，而不是通用启动器参数。这个分工会在第6章详细展开；此处只要知道，`dsh` 选择 Web Profile，Web 插件解释自己的参数。

启动输出会提供带认证信息的访问入口。直接访问未认证地址得到 `401 Unauthorized`，不表示服务器没有启动；它说明服务器已经响应并拒绝未认证请求。使用启动入口建立认证状态后，页面才会返回正常内容。不要把终端打印的认证地址保存进书稿、截图或公开日志。

页面可访问以后还差两步。

第一步是进入“设置 → 模型”，填写 DeepSeek API Key 或配置其他 Provider。模型配置可以立即生效，不需要重启服务器。第二步是选择工作区。工作区没有选中时，输入框保持不可用。

旧稿在 `dsh-v0.1.2-alpha.1` 上曾验证Web服务、配置树与无Key路径。本次修订没有完成新版应用启动，也没有新增真实DeepSeek请求证据；模型响应质量、token使用和网络错误行为仍需使用有效凭据单独复核。旧运行记录不能替代当前提交的启动验收。

> 踩坑提醒
> “页面打开”“模型配置成功”“工作区已选择”“一项任务完成”是四个不同检查点。不要用前一个现象替后一个下结论。

## Web 和 Headless 只是不同入口

Web 适合持续交互。它提供浏览器界面、工作区选择、审批交互和会话查看。Headless 适合执行一项任务，输出结果以后退出：

~~~sh
env DSH_HOME="$PWD/tmp/deepseek-harness-book/runtime-home" \
  pnpm dsh --profile headless "Summarize this repository and identify its main packages."
~~~

这条真实模型命令需要有效凭据。没有 API Key 时，不要反复改参数猜测；使用仓库提供的无 Key 冒烟测试：

~~~sh
pnpm exec vitest run \
  --config vitest.e2e.config.ts \
  apps/cli/tests/profiles/headless/tests/keyless-smoke.e2e.ts
~~~

当前测试源码使用可控模型驱动器，要求真实Loader插件树完成Shell工具往返并持久化Turn；POSIX选择 `bash`，Windows选择 `pwsh`。旧稿曾记录2个文件、23项测试通过，那是旧基线证据。本次只核对了新版测试文件与断言，尚未重新运行，不能把23当成当前通过数。

Web、Headless、SDK、SDK Minimal 和 ACP 都从 `dsh` 与具名 Profile 启动。除刻意独立组装的 SDK Minimal 外，随附的主要应用在相同的基础 Bundle 上增加自己的入口能力。Web 添加 HTTP、认证和浏览器界面，Headless 添加一次性任务解析与结果输出，SDK 和 ACP 添加各自的协议服务。

这意味着你不应该把 Web 和 Headless 当成两套 Agent 内核。它们最终复用模型、Session、工具、Agent 和权限等核心能力，只是在“任务从哪里来、结果送到哪里、进程何时退出”上不同。

把几个随附入口放在一起，会更容易看出差别：

| Profile | 谁发送任务 | 结果主要交给谁 | 进程通常何时结束 |
|---|---|---|---|
| Web | 浏览器中的会话控制层 | 浏览器 UI 与持久 Session | 用户关闭服务时 |
| Headless | 一次性命令行 Runner | 标准输出与持久 Session | 当前任务结算后 |
| SDK | TypeScript 或 Python Client | JSON-RPC Client | Client 关闭或断开时 |
| ACP | 自动化 Client | ACP 协议对端 | 对端断开时 |
| SDK Minimal | SDK Client | JSON-RPC Client | Client 关闭或断开时 |

表中的“谁发送任务”不同，不表示各入口可以绕过 Agent 生命周期。它们最终都要创建或恢复 Session，通过 Agent 句柄驱动工作，并读取事件或结果。入口拥有的是协议和进程生命周期，不是另一套模型循环。

SDK Minimal 也不要简单理解成“比 SDK 少几个工具”。它使用一棵独立列明的极简配置树，适合展示最小 SDK 组合；其他主要 Profile 则以 `dsh-base` 作为共享第一层。第6章会用实际配置行解释这种组合差异。

选择入口时，先看使用场景。需要人查看工具卡片和处理审批，用 Web；需要脚本发起一项任务并读取最终输出，用 Headless；需要另一个程序持续创建、恢复和控制 Session，用 SDK 或相应协议。不要因为 Headless 看起来简单，就在它之外再写一个不经过 `dsh` 的私有可执行入口。

## 无 Key 验证不是“什么也验证不了”

缺少 API Key 时，最常见的两个反应都不理想。一个是停止学习，认为没有模型就看不了 Agent；另一个是用 Mock 跑出一句话，然后把它写成真实模型成功。

更准确的做法是把证据分层：

| 证据层 | 无 Key 能否完成 | 能证明什么 |
|---|---:|---|
| 源码与公开类型 | 能 | 当前版本声明了哪些接口和所有者 |
| 配置导出 | 能 | 某个 Profile 最终准备挂载哪些插件和配置 |
| 单元测试 | 能 | 特定输入、失败和生命周期行为 |
| Mock 端到端测试 | 能 | 真实 Loader、循环、工具和持久化能否组合工作 |
| Web 页面启动 | 能 | HTTP、认证与前端产物是否可用 |
| 真实 Provider 请求 | 不能 | 网络协议、凭据、限流和真实输出 |
| 业务质量评测 | 不能 | 模型是否能可靠完成目标任务 |

当前Headless keyless smoke的模型响应是受控的，测试断言Shell工具产生 `tool/call`，结果和最终输出包含 `CLI_TOOL_ROUND_TRIP`，压缩Session文件可解码且拥有Session header。这些是应由测试运行证明的关系；本次确认源码中存在这些断言，未取得新版通过结果。即使通过，也不证明DeepSeek模型会自主选择同一工具。

这种分层很适合源码学习。先用可控输入把系统行为固定下来，再接入真实模型验证不确定部分。否则一次请求失败时，很难判断问题来自配置、网络、Adapter、模型选择还是 Agent Loop。

## 一项只读任务要观察七件事

配置真实模型和工作区后，可以在 Web UI 输入：

> Summarize this repository and identify its main packages.

这是一项适合作为第一次观察的任务。它不要求修改文件，结果也容易通过仓库目录核对。运行时不要只复制最终摘要，至少记录下面七项：

| 观察项 | 需要记录什么 | 为什么重要 |
|---|---|---|
| 启动入口 | Web 还是 Headless，完整命令是什么 | 决定任务怎样进入系统 |
| Profile | 使用哪个具名组合 | 决定装入哪些能力 |
| 模型 | Provider 与模型 id | 决定请求实际交给谁 |
| 工作区 | 会话使用的项目路径 | 决定文件能力作用范围 |
| 工具 | 调用了读取、搜索还是 Bash | 区分模型记忆与现场证据 |
| 人工决定 | 是否出现审批，选择了什么 | 说明策略怎样限制动作 |
| 终态 | 成功、拒绝、错误还是取消 | 说明系统怎样结算这项工作 |

如果没有真实凭据，也可以用无 Key 测试完成其中的结构观察，并把“模型任务”一栏明确记为未验证。证据不足时缩小结论，比把一次模拟运行包装成真实成功更有价值。

第一次运行记录可以直接使用这个模板：

~~~text
日期与源码基线：
Node.js / pnpm：
启动命令：
DSH_HOME：
Profile：
工作区：
模型 Provider / model：
用户输入：
工具调用：
审批或权限决定：
最终状态：
实际输出：
尚未验证：
~~~

## 出问题时按检查点排查

第一次启动失败，不要把所有错误都归到“项目没装好”。沿检查点逐层缩小问题，通常比重新安装一遍依赖有效。

### 命令还没有进入 Profile

如果提示缺少 `--profile`、参数互斥或命令无效，先运行 `pnpm dsh --help`，检查的是启动器语法。`pnpm dsh web --help` 则会进入 Web Profile，由 Web 应用打印自己的参数。两份帮助不是重复内容。

`--profile`、`--patch` 和配置导出参数必须出现在应用参数以前。启动器遇到第一个不认识的 token 后，会把剩余内容交给应用。把参数放错位置，可能让本来属于启动器的选项被应用接收。

### 配置可以导出，应用却不能启动

这说明组合阶段已经完成，失败更靠后。检查构建产物、插件配置校验、端口占用、宿主沙箱和文件监听权限。受限环境中出现 `listen EPERM`，说明宿主拒绝监听；换端口不一定能解决。需要在允许本地监听的环境原样复核，不能把宿主限制写成项目缺陷。

### 页面返回 401

先看服务是否打印了访问入口，再确认浏览器是否通过该入口建立认证。401 与连接被拒绝不同：前者说明 HTTP 服务正在回应，后者才可能是服务未监听、地址错误或进程已经退出。

### 输入框不能使用

先确认会话工作区是否选中，再检查模型路由是否可用。终端所在目录和配置树里存在默认模型，都不表示当前 Web 会话已经完成这两项选择。

### 模型请求失败

检查 Provider、model、凭据引用和网络端点。没有 API Key 时，错误本身是预期边界。不要为了让请求“先跑起来”把密钥写进 `cordis.yml`、源码或截图；使用环境变量或受管凭据机制。

### 工具没有执行

先确认模型是否真的产生了工具调用，再看参数校验、策略、审批和 Provider。最终回答里出现“我将查询”不等于 Session 中已经出现 `tool/call`；自然语言承诺不能替代执行事实。

### 任务完成却找不到历史

检查 `DSH_HOME`、Session 持久化目录和本次是否创建了另一份隔离 Home。很多“会话丢失”只是下次启动使用了不同 Home。恢复问题先找数据位置和 Session id，不要从界面文字猜。

把这些检查点写进运行记录，下次遇到相似问题时就能直接比较。源码学习最有价值的产物，不是一次顺利截图，而是一套失败以后知道去哪看的方法。

## 从第一次运行看见四层系统

完成一次只读任务后，可以把观察到的东西重新分成四层。

应用层回答任务从哪里进入、结果在哪里展示：Web 页面、Headless 输出、SDK 或 ACP。运行层回答工作怎样开始和结束：Agent、Inbox、Turn、Step 与取消。能力层回答系统能做什么：模型 Adapter、文件、Shell、Subagent 和其他 Provider。事实层回答重启以后凭什么继续：Session Event、持久化和 Projection。

四层之间会协作，但不能互相代替。Web 界面消失，不表示 Session 事实消失；模型 Provider 更换，不应该重写工具注册表；Shell 工具出现，不表示当前策略一定允许执行；Headless 进程退出，也不表示会话没有持久化。

后面的章节会逐层放大。第2章先沿一条消息走过运行层和事实层，第3章学习在仓库里找到这些责任的所有者，第4—6章再解释插件和配置为什么能把它们组装起来。

## 本章回顾：先停在看得见的地方

第一次进入大型 Agent 仓库，很容易顺着一个 import 一直追进模型适配器、Cordis Loader、前端组件和平台沙箱。结果打开了几十个文件，却说不清程序从哪里启动。

这一章的停止点只有四个：

1. 能从源码构建并启动一个受支持的 Profile。
2. 能分清源码目录、Harness Home 和会话工作区。
3. 能解释 Web 与 Headless 共享核心、入口不同。
4. 能用运行记录表区分已验证事实和待验证模型行为。

暂时不要修改 Agent Loop，也不要尝试记住所有 Package。下一章只沿一条消息前进：它怎样进入 Inbox，怎样打开 Turn 和 Step，什么时候调用工具，又把哪些事实留在 Session。

当我们不再只盯着最后一句回答，Agent 才第一次作为一个运行系统出现在眼前。
